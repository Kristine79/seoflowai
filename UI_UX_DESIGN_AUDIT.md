# SEOFlow AI — UI/UX & Design Audit

> Дата: 14.08.2026 · Production: https://seoflowai.vercel.app/
> Метод: полный обзор кода (89 файлов src/), DOM-анализ production-страницы (токены, типографика, контраст, радиусы), проверка API и состояний, benchmark-исследование B2B SaaS (2026).
> Результаты программной проверки: 14 секций, 460 элементов с rounded, 2215 бордеров zinc-200, 112 элементов с font-size 10px, контраст zinc-400/white = 2.56:1.

---

## Executive Summary

SEOFlow AI — **функционально сильный продукт с посредственным UI**. Аудит показывают двойственную картину:

**Что работает (сохранить любой ценой):**
1. **Реальная кампания 77 Platforms с настоящими статусами, URL и отчётом** — это редчайший proof point; ни один конкурент-концепт такого не имеет. Это главный актив продукта.
2. **Hero с живым product-mockup** (реальные данные кампании) — сильный первый экран.
3. **Концепция Human-in-the-loop подана честно** — отличительная идея, уникальная для ниши directory-размещений.
4. **Интерактивный ProductPreview** (табы дашборд/кампании/каталоги/аудит/компания) — редкий пример реальной demo-механики на landing.
5. **Кейс-страница** — грамотно структурирована (H1→H2→H3), содержит доказательства.
6. Чистый код, нулевые console-ошибки на production, 0 horizontal overflow на десктопе.

**Что тянет вниз (главные проблемы):**
1. **AI-slop визуальный язык**: 3-карточные гриды с icon+title+text повторяются 6+ раз; нумерация `01–06` в каждой секции; mono-uppercase микро-лейблы `tracking-[0.18em]` в каждой секции; pulse-точки; одинаковая структура секций «текст слева / UI-панель справа» 5 раз подряд.
2. **Микротипографика**: 9–11px текст на 400+ элементах; контраст zinc-400/white 2.56:1 — провал WCAG AA; emerald-600/amber-600 на белом тоже не дотягивают.
3. **Дублирование визуальных определений**: цвета статусов переопределены в 4 местах с разными названиями (emerald vs green, zinc vs slate vs gray); два «primary» цвета кнопок (zinc-900 и blue-600).
4. **Позиция кейса**: 77 Platforms — секция №10 из 14, после четырёх маркетинговых секций одного ритма. Доказательство тонет в feature-карточках.
5. **Несогласованность app**: английские UI-строки в русском интерфейсе («Start Submission», «Submission Progress»), статичные данные («AI Кредиты 2 450»), сырые технические результаты загрузки (заголовки колонок, sample-строки) вываливаются в UI.
6. **Респонсив**: таблица каталогов — фиксированный 7-колоночный грид без адаптива; overflow на мобильных.

**Вывод:** редизайн нужен не «чтобы красивее», а чтобы (а) убрать шаблонность и дать продукту собственное лицо, (б) поднять контраст/читаемость до профессионального уровня, (в) переставить акценты: доказательство (кейс) — выше, фичи — компактнее. Функциональное ядро не трогаем.

## Product UX

### Что пользователь понимает за первые 5–10 секунд

| Вопрос | Ответ | Оценка |
|---|---|---|
| Кому нужен? | «SEO-каталоги без ручной рутины» + eyebrow «SEO Automation Platform» | 7/10 — понятно, но категория «SEO Automation» размыта (таких инструментов сотни) |
| Что делает? | Hero-подзаголовок объясняет; live-mockup показывает реальную кампанию | 8/10 |
| Какой workflow? | 6 шагов DISCOVER→SELECT→PREPARE→SUBMIT→VERIFY→REPORT видны в mockup и секции Workflow | 8/10 |
| Что будет после создания кампании? | Только через 10+ секций скролла (Case Study) | 4/10 — главный разрыв |
| Что означают статусы? | На landing — хорошо (5 цветных статусов в кейсе). В app — 9 статусов, два почти неразличимы | 6/10 |
| Что делать сейчас? | CTA «Начать кампанию» ясен, но ведёт в app без авторизации | 5/10 |

### Ядро продукта: DISCOVER → ANALYZE → PREPARE → SUBMIT → VERIFY → REPORT

- **На landing**: представлено дважды (Workflow секция №3 + mockup в hero) — хорошо, но в разных формулировках: «Анализ/Приоритизация/AI-подготовка/Подача/Проверка/Отчёт» (русские) и «Audit/Select/Prepare/Submit/Verify/Report» (английские, в mockup). Два словаря для одного процесса — путает. **Нужен единый набор названий этапов** на русском, и он должен совпадать в hero, workflow, product-preview, campaign-card и app.
- **В app**: workflow-степпер есть только на странице кампаний и в карточке кампании; сам степпер не кликабелен (не навигация), этапы не показывают, сколько платформ на каждом — только декоративная полоса. Упущенный потенциал: степпер должен быть **состоянием и навигацией одновременно**.
- **Статусы**: в app 9 статусов; `WAITING_VERIFICATION` и `VERIFICATION_REQUIRED` имеют одинаковый цвет (orange) и похожие названия («Ожидает модерации» / «Требуется действие»); `NEEDS_MANUAL` в automationJobs имеет собственный набор слов. Пользователь не сможет отличить их на вкладке фильтров. Требуется единая статус-модель с иерархией: группа (done/attention/blocked) → статус → next action.

### Места, где пользователь может потеряться

1. **После создания кампании** — нет первого-шага-гида: созданная пустая кампания не подсказывает «загрузите Excel → запустите аудит → подготовьте контент». Empty state есть, но это статичный текст без последовательности действий.
2. **Загрузка Excel** — двухшаговый неочевидный flow (выбрать файл в карточке кампании → появляется отдельная карточка «Загрузка {file.name}» внизу → кнопка «Загрузить и обработать»). Результат загрузки выводит developer-детали: «Заголовки: Name | Website | ...», «Строк обнаружено: 250», «Первые: ... Последние: ...». Это полезно инженеру, не пользователю. **P1**.
3. **Страница каталога (detail)** — 1070 строк, правый сайдбар из 5-7 карточек, английские подписи. Высокая когнитивная нагрузка; пользователь не видит, что главное.
4. **Dashboard** — данные противоречивы: карточка «AI подготовлено: 16» с подписью «Контент готов для 91 платформ» (16 ≠ 91). Пользователь перестаёт доверять цифрам. **P1**.
5. **Sidebar «AI Кредиты 2 450»** — статичная заглушка в продукте с реальными данными. Убивает доверие сильнее любой ошибки. **P1** (в идеале P0 — это видно на каждой странице).

### Human-in-the-loop в UX продукта

Принцип «AI автоматизирует, человек решает» на landing подан отлично (секция HITL, 3 состояния). Но **в самом продукте этот принцип не выражен визуально**:

- Нет единого компонента «требуется человек»: NEEDS_MANUAL в истории подач — жёлтая карточка с `⚠`; needsHuman на landing — amber; VERIFICATION_REQUIRED — orange badge. Три разных визуала одного понятия.
- Нет очереди человеческих действий (human-queue): «23 требуют действия» есть на marketing-карточке, но в app нет экрана/бейджа «N задач требуют человека — начать». Human-in-the-loop — фича продукта, а в UI она не представлена как первый-class элемент. **P0 для продукта** — это его главная дифференциация.
- Нет подтверждений успеха (success toasts) после «Завершить», «Скопировано» — есть только у копирования текста.

### Narrative flow

Hero → Проблема → Решение(workflow) → Возможности → HITL → Продукт → Кампании → Аудит → Контент → **Кейс** → Отчётность → Аудитория → Почему → CTA.

**Проблема позиционирования:** сильнейшее доказательство (реальная кампания с URL-ссылками на профили) стоит после трёх однотипных секций «фича + панель». Benchmark 2026 (roast.page, 1000+ страниц): «83% топ-страниц показывают продукт/доказательство выше первого экрана; quantified proof даёт +6–10 баллов Trust». Секции 7–9 (Campaign/Audit/Content showcase) — по сути три пересказа одной истории (AI подготавливает, человек проверяет, всё фиксируется). Они каннибализируют друг друга и отодвигают кейс.

**Предложение (без новых секций):**
- Объединить 7–9 в одну секцию «Продукт: кампания = единый контекст» с табами (или компактный 2-колоночный блок).
- Поднять Case Study сразу после Hero (или после Problem). Минимум — перед фичами.
- 12 (Audience) и 13 (Why) поменять местами не обязательно; обе компактнее.

### Пять вопросов покупателя

1. **Какую проблему решает?** — Да, секция Problem конкретна (×77). ✅
2. **Как решает?** — Да, workflow + демо. ✅
3. **Чем отличается от обычных SEO-тулов?** — HITL + evidence; но это в секциях 5 и 11, а не на первом экране. Частично. ⚠️
4. **Почему доверять?** — Реальные URL профилей (Wellfound, FindUsHere, Semfirms — настоящие ссылки) есть в кейсе, но глубоко внизу. ⚠️
5. **Что делать дальше?** — CTA повторяется, но вёл бы в пустой app без демо-данных. ⚠️

### Конкретные замечания

- **Hero H1 «SEO-каталоги без ручной рутины»** — 6 слов, outcome-ориентирован. Хорошо. Но eyebrow «SEO AUTOMATION PLATFORM» — generic-лейбл; его заменить на продуктовую категорию: «Directory & Citation Campaigns».
- **Секции 7–9**: одинаковая геометрия (`grid lg:grid-cols-2` + Reveal delay) — монотонный ритм на 60% длины страницы.
- **Case Study**: таблица с фильтрами и 50 площадками — отлично; но заголовок секции и кнопка «Скачать полный отчёт» — бесшовная интеграция proof; **перенести выше**.
- **Footer**: «Privacy» и «Terms» — `<span class="cursor-default">`, не ссылки. Для B2B-продукта это признак незавершённости и юридический риск. **P1**.
- **No testimonials / FAQ / pricing**: по benchmark FAQ/пруф рядом с CTA добавляют доверия, но по задаче мы не добавляем секции автоматически — улучшаем существующее; упоминание в roadmap как опция.
- **CTA-цепочка**: «Начать кампанию» ведёт на /campaigns (продукт). Пользователь попадает в приложение без демо-контента. Для conversion: либо seed-демо-кампания «77 Platforms» при первом заходе, либо landing-CTA «Смотреть кейс» как первичный для неавторизованных. **P1**.

## Dashboard

### Главный вопрос: WHAT IS HAPPENING? / WHAT NEEDS MY ATTENTION? / WHAT SHOULD I DO NEXT?

**WHAT IS HAPPENING?** — Да, частично: 4 stat-карточки + «Распределение по приоритетам» + «Ход кампании». Но «Ход кампании» = 5 строк «label — число» + progress bar 0% (в текущих данных completed=0 → бар пуст, хотя 160 готовы к подаче — прогресс 0% при 90% работы впереди/позади? Прогресс считается по completed/total — некорректен: «готовые к подаче» не считаются прогрессом, хотя это главное состояние).

**WHAT NEEDS MY ATTENTION?** — «Что делать дальше» — единственный блок внимания; логика `nextActionReady → needsVerification → needsAction → done` — хорошая идея, но:
- если есть И 160 готовых, И 23 требующих действия — покажется только первый; нет сводки «вниманию подлежит: 2 группы».
- 4-я stat-карточка «Высокий приоритет: 5» с подписью «Готовы к подаче» — мешает две метрики (priority ≠ readiness). **P1**.

**WHAT SHOULD I DO NEXT?** — Блок «Что делать дальше» отвечает, но его CTA-кнопка справа «Продолжить →» не совпадает с основным «К подаче» в теле блока (две кнопки разных действий в одном блоке — конфликт). **P2**.

### Числовые несоответствия (потеря доверия)

- «AI подготовлено: 16» / подпись «Контент готов для 91 платформ» — 16 ≠ 91. **P1**
- `recentDirectories` показывает «Ожидает» для всех — ок, но без дат/приоритета; малоинформативная лента.
- Сайдбар «AI Кредиты 2 450» статичен — см. выше. **P1**

### Плотность и структура

- Дашборд — 6 карточек одного типа (`Card` с заголовком), вертикальный стек: stat-грид, 2 колонки, «Что делать дальше», «Последние каталоги». Это рабочий, но «табло»-вид: нет визуального веса у «внимания», нет приоритизации на экране. Редизайн: блок «Требует внимания» — цветная секция с реальной нумерацией групп (ready/verify/human), список «следующих действий» вместо одной.
- Нет графика динамики (timeline подач) — для рабочего инструмента не критично, но «прогресс по времени» (submitted per day) был бы лучшим single chart, чем бары приоритетов.

### Предлагаемая структура дашборда (P0-план)

```
┌ Header: Главная · CTA «Новая кампания» ┐
├─────────── ATTENTION BLOCK (цветной) ──┤
│  • 160 готовы к подаче → [К подаче]     │  ← единственный акцент экрана
│  • 23 требуют человека → [Открыть]      │
│  • 14 заблокированы (инфо, не алерт)    │
├──────────────────────────────────────────┤
│ Stats row (4 компактные метрики)        │
│ Progress по этапам DISCOVER..REPORT     │  ← 6-шаговый степпер с counts
│ Recent platforms (таблица с next action)│
└──────────────────────────────────────────┘
```

## Design System

### Текущее состояние токенов

`globals.css` содержит всего 2 CSS-переменные (`--background`, `--foreground`). Вся система — инлайновые Tailwind-классы. Это значит: **системы нет, есть конвенция**. Конвенция неплохая (zinc + blue-600 + emerald/amber/rose), но:

| Аспект | Факт (замер) | Проблема |
|---|---|---|
| Радиусы | 0, 4, 6, 8, 12, 16, 9999 — 7 значений | нет scale; button=8, card=12(UI)/16(marketing), badge=9999 |
| Бордеры | zinc-200 #e4e4e7 — 2215 использований | «окантовочный» дизайн: каждый элемент в рамке |
| Тени | shadow-sm — 91+ элемент | shadow-sm на всех карточках + кастомные большие тени в hero |
| Типографика | 9, 9.5, 10, 11, 12, 14, 15, 16, 18, 24, 36, 48, 54.4px | 5 размеров < 12px; нет type-scale |
| Шрифты | Geist (sans, 1 начертание) + Geist Mono | нет display-акцента, нет character |
| Цвета статусов | zinc/slate/gray + emerald/green + amber/yellow/orange + rose/red — 4 «палитры-клоны» | `getStatusColor` (slate), `getAutomationColor` (gray/green/yellow), badge (emerald/amber/rose) — в одном приложении 3 системы |
| Кнопки | `default` = zinc-900 (используется в app), `primary` = blue-600 (маркетинг + detail page) | два «главных» цвета |
| Поля | Input h-10 rounded-lg — ok; textarea — дублированный inline-класс в 3 местах | нет компонента Textarea |
| Progress | компонент (bg-zinc-900) + инлайн-бары (bg-blue-600/emerald) в маркетинге | две реализации |
| Иконки | lucide — единый источник ✅ | — |
| Badge | 6 вариантов ✅ | но статус-цвета не используют Badge-варианты |

### Дублированные определения статус-цветов (главный источник рассинхрона)

1. `src/lib/utils.ts` — `getStatusColor` (slate/green/orange/purple)
2. `case-study.tsx` — `STATUS_STYLE/STATUS_DOT` (emerald/blue/amber/rose/zinc)
3. `product-preview.tsx` — `STATUS_META` (то же, третья копия)
4. `campaigns/page.tsx` — инлайн-классы статусов в карточке кампании
5. `directories/[id]/page.tsx` — `getAutomationColor` (green/yellow/orange/red/gray)

**Итог:** один статус в 3–4 местах с разными оттенками. Любое «починить цвет» — правка 4 файлов. Решение: единый `statusMeta`-маппинг в `src/lib/status.ts` + компонент `StatusBadge`/`StatusSelect`.

### Таблицы

- `directories/page.tsx`: грид-таблица (не `<table>`): 7 колонок фикс. ширин, **без адаптива** — на <900px будет horizontal overflow. **P1**
- `case-study.tsx`: грид-таблица, на мобильных переключается в карточки ✅ — хороший паттерн, перенести в app-таблицы.
- Ячейка-Select (h-7) — кликабельная зона 28px < 44px. **P2**

## AI Slop Audit

Методика: проверка по 18 признакам с замером по коду и DOM.

| # | Признак | Где | Серьёзность | Комментарий |

## Visual Identity

**Текущее:** white/zinc + blue-600 + тёмные акценты (zinc-950) + Geist + mono-лейблы. Ухоженный, нейтральный, но «безликий»: такой же визуал у сотен AI-startup-лендингов.

**Что сохранить:**
- Белый/светлый интерфейс и тёмные секции (рабочий контраст);
- Спокойная основа (zinc) — не уходить в кричащее;
- Реальные данные как визуальный материал (статусы, цифры, URL);
- Geist как sans-основу (производительность, современность).

**Что усилить (предложения идентичности):**
1. **Signature-элемент**: «статус-лента»/«статус-глиф» — визуальный язык, в котором статус платформы — базовый атом продукта (точка + цвет + mono-метка). Сделать его сквозным: маркетинг, дашборд, таблицы, бейджи. Это превращает уникальную бизнес-идею (каждый шаг имеет статус) в уникальную визуальную идею.
2. **Второй цвет**: выбрать один поддерживающий цвет (например, глубокий teal/cyan для «автоматизации» и тёплый amber для «человека» — система «AI vs Human»). Синяя пара + amber создаёт визуальный язык HITL: синий = система, янтарный = человек.
3. **Типографический акцент**: добавить display-гротеск с характером (например, Inter Tight/Space Grotesk) для заголовков и цифр; mono оставить для данных/статусов. Geist Mono уже неплохо работает — использовать mono как «голос данных», не как «голос декора».
4. **Убрать**: mono-uppercase в каждом разделе (оставить только у реальных данных), лишние нумерации, бордер на каждой карточке (бордеры заменить на tiered surfaces: белый фон + лёгкая тень для главных, бордер для второстепенных).

**Цель:** «credible technical product»: плотность как у Linear/Retool, доказательства как у G2-страниц, статусная эстетика как у мониторинговых инструментов (PagerDuty/Grafana), но светлая и дружелюбная.

**Находки:**
1. **Мелкий текст**: 10px — 112 элементов, 11px — 281, 9.5/9px — единично. Минимум для secondary-текста: 12px; для критичных подписей 13–14px. **P1**
2. **Контраст статусных цифр** (emerald/amber на белом) — провал; в stats-карточках и кейсе это ключевые цифры. Поднять до 700-shade: emerald-700 (#047857, 4.55) / amber-700 (#b45309, 4.5). **P1**
3. **Scroll-reveal**: `.reveal { opacity: 0 }` применяется серверно; при недоступном/сломанном JS контент остаётся невидимым. Нужен `no-js`-гард или старт-состояние `opacity: 1` с `motion-safe` активацией. **P1**
4. **Дублированный DOM для mobile/desktop** (workflow, evidence chain): скрытый дубликат читается скринридерами дважды — `aria-hidden`/`sm:hidden` недостаточно для семантики; добавить `aria-hidden` на скрытые копии. **P2**
5. **Фокус**: shadcn-компоненты имеют focus-visible ring ✅; маркетинговые кастомные CTA — полагаются на дефолтный outline браузера (не отключён префлайтом, но не стилизован) — непоследовательно. **P2**
6. **Тап-таргеты**: Select h-7 в таблице (28px), фильтр-чипы — меньше 44px. **P2**
7. Заголовки: структура H1→H2→H3 соблюдена на landing и кейсе ✅.
8. `alt` отсутствует у 0 изображений (их почти нет) ✅; иконки декоративные — aria-hidden не везде проставлен (lucide внутри кнопок без label — есть aria-label у burger; у остальных icon-only кнопок нет). **P2**

## Motion

**Что есть:** scroll-reveal (fade-up 14px, threshold 0.12), `animate-grow-x` для баров, `pulse-dot`, `fade-in` при смене табов, prefers-reduced-motion полностью обработан ✅ (редкость, спасибо).

**Оценка:** motion уже сдержанный и решает задачи:
- grow-x на прогресс-барах объясняет состояние ✅
- fade-up reveal — приятен, но применяется почти ко всему (монотонность). Уменьшить частоту: reveal только у крупных блоков, не у каждой карточки с delay 100/200.
- Нет motion, объясняющего workflow между экранами (например, при смене статуса платформы — подсветка строки).

**Рекомендации (точечно):**
1. При смене статуса в таблице — краткая подсветка строки (state-change motion). **P2**
2. В ProductPreview добавить микро-переходы табов (уже есть fade-in ✅).
3. Не добавлять: parallax, floating-анимации, декоративные gradient-дрифты. Ничего не отнимать у reduced-motion.

## Design Principles

1. **Статус — это продукт.** Каждый элемент (платформа, кампания, шаг) имеет состояние; интерфейс обязан показывать состояние, причину и следующее действие всегда вместе. Единый визуальный атом: точка-статус + метка + next action.
2. **Доказательство прежде слов.** Реальные URL, скриншоты, статусы — визуальный материал; декоративные элементы не имеют права конкурировать с ними.
3. **Два голоса:** синий = автоматизация (система делает), янтарный = человек (твоё действие). HITL — сквозная цветовая семантика, а не секция лендинга.
4. **Один фокус на экран.** Дашборд отвечает на WHAT IS HAPPENING / WHAT NEEDS ATTENTION / WHAT NEXT — в этом порядке, с одним акцентом.
5. **Меньше рамок, больше поверхностей.** Не каждую карточку обводить: иерархия фона (white > zinc-50 > zinc-100) + бордер только у интерактивного.
6. **Читаемость — B2B-минимум:** ≥12px secondary, ≥14px body, AA-контраст на всём.
7. **Один словарь:** этапы, статусы, кнопки — единые названия на всех поверхностях (маркетинг = продукт).
8. **Движение объясняет, не украшает.** Reveal только у крупных блоков; анимации состояния (смена статуса, переходы табов) приоритетнее декора.
9. **Не ломать работающее:** hero-мокап, ProductPreview, кейс-таблица, HITL-секция, reduced-motion — сохранить как есть по сути.

## REDESIGN STRATEGY

**1. Visual direction.** «Операционная панель, которая доказывает»: светлый инструментальный интерфейс (белый + zinc), статус-лента как фирменный атом, доказательства (URL/скриншоты/статусы) как главные визуальные объекты. Тёмные секции — только для философии (HITL, CTA). Никаких декоративных градиентов-заливок: один контекстный градиент в hero, один в CTA.

**2. Landing architecture.** Hero → Proof (URL-профили) → Кейс 77 → Проблема → Workflow → HITL → Продукт (табы) → Отчётность → Аудитория/Принципы → CTA. Narrative: «доказано работой» → «проблема» → «как устроено» → «почему это иначе».

**3. Dashboard direction.** Рабочий инструмент, не табло: один attention-блок с группами действий; прогресс по 6 этапам с количеством платформ; таблица «платформа → статус → next action»; никаких декоративных карточек ради сетки.

**4. Component strategy.** shadcn-база сохраняется; добавляются продуктовые компоненты поверх: StatusBadge/StatusSelect/StatusDot, AttentionBlock, HumanActionQueue, NextActionRow, EmptyStateChecklist, WorkflowStepper (навигация с counts). Убрать дубли (Progress, статус-стили, textarea).

**5. Typography.** Geist sans (body/UI) + Geist Mono (данные, статусы, URL) + один display-гротеск для заголовков (опц. Space Grotesk 600–700). Scale: 12/14/16/20/36/48. Мелкие mono-капсы — только у реальных данных.

**6. Color.** Базовый zinc (900/500/400-только-для-неважного), primary blue-600 (система), amber-500/600 (человек), emerald (размещено), rose (блок), плюс один нейтральный surface-zinc-50/100. Один цвет линий zinc-200. Убрать slate/gray/green/yellow-клоны.

**7. Spacing.** Единый ритм: секции py-24/32, карточки p-5/6, гриды gap-4/5/6. Инлайн-пиксели (только в исключениях).

**8. Motion.** Reveal только для крупных блоков (без delay-каскадов по карточкам); grow-x для прогресса; fade для табов; новый: подсветка строки при смене статуса. Respect reduced-motion (уже есть).

**9. AI-slop prevention.** Правила: (а) не более 1 icon+title+text грида на страницу; (б) нумерация только для реальных последовательностей; (в) mono-капсы — только у данных; (г) одна панель-доказательство на экран; (д) перед добавлением новой карточки — спросить «это факт или декорация?».

**10. Product identity.** «Система, которая честно работает»: статус-лента (точка+цвет+монометка), URL-профили как визуальные доказательства, amber-язык человеческих действий, реальные цифры кампаний. Узнаваемость через операционную честность, а не через декоративный стиль.
